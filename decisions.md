# Motif.Is.Core: decisions so far

Motif.Is.Core is the small, stable core of [Motif.Is](https://github.com/motif-dotnet/Motif.Is), a proposition library for .NET specs. It was designed from Motif.Is's decisions and rethought where a small core called for it. Decisions 1–5 are carried over from Motif.Is; the rest are the core's own.

| # | Topic | Decision |
|---|---|---|
| 1 | Principle | Benefits to the library's users come first: claims read in a spec like good English propositions. Second, failures read well: clear first, and succinct where possible. The internals and the core's own specs come after those. An API is judged from its call site in real specs, not in the abstract. |
| 2 | Failures | The exception is `Motif.Expected`, because test runners print the full type name before the message, so the name starts the sentence: ``Motif.Expected : `order.Placed` to be true`` / `but it's false.` "Expected … to be" over "is … but it is", and "it's" over "it is". Every failure ends with a full stop, unless what was found already ends with one. |
| 3 | No test framework reference | The core works with any test framework, and references none. xUnit v3 treats an exception as an assertion failure when it implements an interface named `IAssertionException` from any namespace, so the core has its own, internally. It changes how xUnit classifies a failure (an assertion, not an error), not how it reads: the type name starts the sentence either way. The core's own specs run on xUnit v3. |
| 4 | Subjects | A subject's name is its source text, through `CallerArgumentExpression`. For code, a lambda's `() =>` is dropped. |
| 5 | Spec names and the failure gallery | After Kevlin Henney: namespace, class and method together read as one proposition (`A_subject.claimed_to_be_what_it_is.holds`), and specs that share the start of a sentence share a namespace or class, so `.editorconfig` turns off CS8981 for `Checks/`. `Example_failures` holds specs that fail on purpose, a class per claim (`Example_failures.Is.when_false`), tagged `Kind=FailureGallery`, to show the messages in a test runner; CI leaves them out. |
| 6 | Foundation | Motif.Is is rebuilt on the core: claims and failures live in one place. Motif.Is's specs are checked by a pinned core release, a different package from the code under test, so they need no extern alias. A separate frozen checker, with every claim written twice, was turned down. |
| 7 | Propositions stay internal | Every claim builds a proposition (subject, claim, expectation, claimed, holds, found), and its failure is made from it, but nothing outside the core sees it: no hook for observers, no recording. Adding public API later breaks nobody, and removing it breaks every user, so a hook waits for a real user, such as plain-English specs in Motif.Is. When it comes, a global observer would mix up specs running in parallel. |
| 8 | Audience | Designed for anyone: careful names, a public API to be happy to freeze, docs. Released to Motif's own repos first, and to nuget.org once the API has stood up to real use. Until then a rename is one deliberate commit. |
| 9 | Two claims | `Is` and `Throws<T>`, and nothing else. `Is` covers true, false and null: `order.Placed.Is(true)`, `order.Discount.Is(null)`. Motif.Is builds `IsTrue`, `HasCount`, `Includes` and the rest on 11, so the extension point has a real user from the start. |
| 10 | Sequences | `Is` compares sequences item by item, whatever their collection types, all the way down, but not strings, which compare whole. Otherwise `list.Is([1, 2])` would fail with *but it's [1, 2]*. Order counts, sets and dictionaries included, for now. |
| 11 | Making a claim | One public method, `Claim.That(subject, holds, expectation, found)`, which `Is` uses too, so the core's own specs test it (24 says why `Throws` doesn't). It writes *found* with the core's formatter (*it's 3*), so custom failures read like the core's, and the phrase can be overridden (*it has 2 items*). The subject comes from `CallerArgumentExpression` on the claim author's own parameter: leave it off and the subject is lost. A public `Expected` constructor and a fluent builder were turned down. |
| 12 | Claims about snippets | `Check.That(() => order.Place()).Throws<X>()`, for now ([Motif.Is#4](https://github.com/motif-dotnet/Motif.Is/issues/4) stays open), to be judged from real specs before nuget.org. If `Check.That` and `Claim.That` get confused, the extension point is renamed: it has fewer users. |
| 13 | Name | Package and repo `Motif.Is.Core`, namespace `Motif.Is`, so specs read the same whichever package they use, and Motif.Is keeps its name and history. A build can have only one version of a package, so Motif.Is and its specs use the same core release. |
| 14 | Target | `net10.0` only: .NET 8 and 9 reached end of support on 10 November 2026, so it's the only supported LTS. Targets are added when needed, which breaks nobody. |
| 15 | Its own specs | A few bootstrap specs, in the `Bootstrap` namespace so they show as a group in a test runner, use [AwesomeAssertions](https://github.com/AwesomeAssertions/AwesomeAssertions) (Apache-2.0) to prove that a false claim throws and that `Throws` catches, with a `using` in their own files only, so `Should()` stays out of the self-hosted specs. It reads better than plain xUnit `Assert`, which was the first choice. Every other spec is written in the core, so the specs are call-site examples. Breaking the core on purpose must fail specs, a check run by hand or with Stryker. |
| 16 | Serving | Each Motif repo that uses the core commits its `.nupkg` to a local feed folder, named in its `nuget.config`. Moving to a newer core is a deliberate commit. GitHub Packages was turned down for now, because restoring from it needs an access token even for public packages; it's worth another look if more repos adopt the core. |
| 17 | Something else thrown | A snippet claimed to throw one type that throws another fails with *but it threw FormatException.*, the type alone, and keeps the original as `Expected`'s inner exception, which test runners print under the sentence with its message and stack trace. The type and its message in the sentence were turned down: the message would show twice, and can be long or run over lines. |
| 18 | Throws and subtypes | `Throws<ArgumentException>()` holds when the snippet throws `ArgumentNullException`, as a `catch` does and as English reads it. A claim of the exact type belongs in Motif.Is ([Motif.Is#8](https://github.com/motif-dotnet/Motif.Is/issues/8)). |
| 19 | Strings in quotes | Strings read in double quotes and chars in single quotes, so a failure tells `"3"` from `3`, and `""` from a space. Strings holding quotes or line breaks print as they are, until one comes up. |
| 20 | Any culture | What's claimed and found reads the same on any machine: numbers in the invariant culture, dates and times in ISO order (`2026-11-14 15:49:00`, with `+01:00` for an offset), and fractions of a second only when they aren't zero, with as many digits as they need. |
| 21 | Subjects over several lines | A subject written over several lines reads on one, so the failure keeps its two lines: each line break and the indentation after it become one space, or none before a leading dot. How long a subject may be, and shortening it, wait for a real one, with long sequences (Later). |
| 22 | Found as a value or a phrase | `Claim.That`'s *found* is either what was found, which the core writes as *it's 3*, or a phrase that replaces it (`found: $"it has {n} items"`). Always a phrase, and a public formatter, were turned down. A more fluent way to make a claim may come later ([#4](https://github.com/motif-dotnet/Motif.Is.Core/issues/4)). |
| 23 | Holes in phrases | The expectation and found phrases are interpolated string handlers, `Expectation` and `Found`, so each hole is written as the core writes what it claims and finds: quotes, any culture, a type as its name. An expectation can also be a plain string; *found* can't, and is a struct, so a string or `null` passed as *found* is what was found. |
| 24 | Claims about snippets | Nothing outside the core can make a claim about a snippet yet, and `Throws` isn't made with `Claim.That`, because it hands back what was thrown and keeps anything else as the inner exception. How it's done waits for a second snippet claim, Motif.Is's exact-type claim, whose likely shape is on [Motif.Is#8](https://github.com/motif-dotnet/Motif.Is/issues/8). |
| 25 | xUnit v3 | The core's own specs run on xUnit v3, the version new users pick. Tried first: with or without `IAssertionException`, v3 prints `Motif.Expected : …` in `dotnet test`, its own runner and its reports, so decision 2 holds there too. |

## Later

- **Checking by the previous release**: spec the core with its own last release under an extern alias, as a compiler is built by its previous release ([#2](https://github.com/motif-dotnet/Motif.Is.Core/issues/2)), after the first release.
- **Async snippets**: `Throws` for a snippet that returns a task, which needs its own `Check.That` and an awaitable `Throws`, as new public API ([Motif.Is#5](https://github.com/motif-dotnet/Motif.Is/issues/5)). Until then an `async` lambda passed to `Check.That` compiles as `async void`, which `Throws` can't catch.
- **Long sequences in failures**: how they print, once one comes up. Consider then putting the subject on the first line and lining up *to be* and *but it's*, so what was claimed and what was found are easy to compare when they're long. Short ones keep the sentence. Lining the second line up with the first isn't possible, because each test runner adds its own prefix to the first line.
